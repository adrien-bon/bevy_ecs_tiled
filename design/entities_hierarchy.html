Entities Hierarchy and Marker Components

When a map is loaded, it spawns many entities: for the map, for layers, for tiles, for objects, for colliders, and more.
To keep things organized, these entities are structured in a parent/child hierarchy, and every entity has an associated marker component to help with queries and system targeting.

Using a hierarchy also enables inheritance of certain components from top-level entities down the tree.
For example, if you change the Visibility of a layer entity, it will automatically apply to all entities below it in the hierarchy, such as tiles or objects.

Whatever their level in the hierarchy, entities spawned by bevy_ecs_tiled share a few common components:

  • TiledMapReference: the map entity they belong to, so you do not have to walk up the hierarchy to find it.
  • TiledName: the name given in Tiled to the layer, tileset or object.
  • A Tiled identifier, such as TiledLayerId or TiledObjectId, to retrieve the raw Tiled data.

World

A world is the optional top of the tree.
Loading a .world asset gives you a TiledWorld entity, which holds a handle to the corresponding TiledWorldAsset.

Each map of the world is spawned as a child of this entity.
All map-level settings can be added to the world entity: they are propagated down to every underlying map.

Map

Loading a .tmx asset gives you a TiledMap entity, which holds a handle to the corresponding TiledMapAsset.
It is the top of the tree, unless the map belongs to a world.

This is where you put map-level settings, such as the TilemapAnchor or the TiledMapLayerZOffset.
It also holds a TiledMapStorage component, which maps Tiled IDs to the spawned entities and the other way around.

Layers

Each Tiled layer is spawned as a child of the map, with a TiledLayer component.
Its value tells you the kind of layer, and what you will find below it:

VariantChildren
TiledLayer::Tilesone TiledTilemap per tileset
TiledLayer::Objectsone TiledObject per object
TiledLayer::Imagea single TiledImage
TiledLayer::Groupother layers, nested as in Tiled

Tiles

Tiles are stored in two levels:

  • Below each TiledLayer::Tiles, there is one TiledTilemap entity per tileset used by the layer. It holds the TilemapBundle from bevy_ecs_tilemap, so this is where the tilemap size, grid size or texture live.
  • Below these tilemaps are the actual TiledTile entities, one for each tile of the layer using this tileset. They are identified in Tiled by their TiledTilesetId and TiledTileId, and positioned with a TilePos.

Objects

Each Tiled object is spawned as a child of its TiledLayer::Objects, with a TiledObject component describing its shape (point, rectangle, polygon, …).
Most objects are a single entity, but two kinds of objects have children holding their visual.

Tile objects

A TiledObject::Tile has a child entity with a TiledObjectVisualOf component.
This child holds the Sprite of the tile and, if the tile is animated, a TiledAnimation.
From the object entity, you can reach it through the TiledObjectVisuals relationship.

Text objects

A TiledObject::Text is rendered using two nested entities, if the text feature is enabled (it is by default):

  • a TiledObjectTextBox child, which represents the text box drawn in Tiled: its Aabb has the size of the box.
  • below it, a TiledObjectText entity holding the actual Text2d and TextFont. Its Anchor and position inside the box follow the horizontal and vertical alignment set in Tiled.

To change the text content or style at runtime, query the TiledObjectText entity:

#![allow(unused)]
fn main() {
use bevy::prelude::*;
use bevy_ecs_tiled::prelude::*;

fn make_texts_red(mut texts: Query<&mut TextColor, Added<TiledObjectText>>) {
    for mut color in texts.iter_mut() {
        color.0 = Color::srgb(1., 0., 0.);
    }
}
}

See the map_text example for a demo.

Images

An image layer has a single TiledImage child, holding the Sprite of the image.
When the image is repeated along an axis, the sprite size is updated to cover what the camera can see.

Physics Colliders

At the bottom of the hierarchy, you find physics colliders.
They are spawned as children of their source, either a TiledLayer::Tiles or a TiledObject, and carry:

  • a TiledColliderOf relationship pointing to their source entity. On the other side, the source has a TiledColliders component listing all its colliders.
  • a TiledColliderSource component telling whether the collider comes from a tiles layer or from an object.

See the physics guide for more information.

Transform and Visibility Propagation

Bevy automatically propagates Transform and Visibility components down the entity hierarchy.

In practice:
If you change one of these components for a top-level entity (e.g., a layer), it will propagate down and apply to all child entities. For example:

  • Adding Visibility::Hidden to an object layer will hide all objects in that layer.
  • Moving an object layer will also move all objects it contains.

Special case for tiles:
Tiles are not rendered as individual entities, but as part of a “chunk” of several tiles for performance reasons.
Each individual tile entity does not have its own Transform or Visibility component.
Instead, these components are propagated down to the TiledTilemap, and bevy_ecs_tilemap handles updating the corresponding tile chunks.

Important:
Even though you technically could, you should not add Transform or Visibility components to individual tile entities:

  • It will not have the intended effect—everything is handled at the tilemap level.
  • It may hurt performance significantly.
